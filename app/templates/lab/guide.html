Security Laboratory Demonstration Guide

Reference manual for instructors and presenters. Use this guide to walk through reproducible demonstrations of the SQL Injection Full Attack Chain (Reconnaissance to Account Takeover), Stored Cross-Site Scripting (In-Session Phishing), and Reflected Cross-Site Scripting (Silent Action Hijacking).

CWE-89

1. SQL Injection (SQLi) — Full Attack Chain

Description & Root Cause: Untrusted user input is formatted directly into SQL query strings rather than bound using parameterized queries. This enables a realistic two-phase attack chain: first dumping users and hashes via search, then bypassing authentication to take over the administrator account.

Target Features: Post Search (:5000/) and Account Login (:5000/login)

Demonstration Steps

  1. Toggle mode to Vulnerable Mode via the top bar switch on this guide.

Phase 1: Reconnaissance & Data Exfiltration (Search)

An unauthenticated attacker explores the public search bar at the home page. They enter a UNION payload to dump all user records and password hashes:

The blog feed immediately displays all 8 user records from the users table, exposing usernames (including admin and alice) and their Argon2id password hashes.

Phase 2: Account Takeover via Authentication Bypass (Login)

Having identified that admin and alice exist, the attacker navigates to :5000/login. Using their knowledge of Alice's account (password: alice123), they substitute Admin's password hash with Alice's hash:

In the Password field, enter Alice's valid password:

Result: Authentication succeeds! The application logs the attacker directly into the admin account (User ID: 1) without modifying the database or needing the admin's original password.

Expected Behavior

Vulnerable Mode: Both phases succeed. The search query leaks credentials, and the login query substitutes Admin's record with Alice's hash, passing the Argon2id check.

Secure Mode: Parameterized queries treat the payloads as literal strings. Search displays "No posts matched your search query", and login returns 401 Invalid username or password.

Source Code Reference: app/routes/blog.py:index() & app/routes/auth.py:login()
CWE-79

2. Stored Cross-Site Scripting (XSS) — In-Session Phishing Attack

Description & Root Cause: User-submitted comment text is stored raw in the SQLite database and later rendered in HTML templates using Jinja2's | safe filter without escaping. This allows an attacker to inject arbitrary HTML and JavaScript that executes in the security context of any victim viewing the post.

Target Feature: Post Comments (:5000/posts/1#comments)

Prerequisites: Sign in with an account (e.g., alice / alice123, register a new account, or use the SQLi login bypass) to read full articles and unlock the comment form.

Live Credential Listener: /lab/attacker (Attacker Control Panel)

Copyable Demonstration Payloads

Triggers only when the victim is signed in (pre-filling their username) and records sessionStorage so refreshing the page does not repeat the prompt. Open a new tab or clear session storage to demo again.

Countermeasure Comparison

Vulnerable Mode: The template in app/templates/blog/post.html uses {% raw %}{{ comment.content | safe }}{% endraw %}. The browser parses and executes the injected HTML elements and JavaScript tags unconditionally.

Secure Mode: Context-aware output encoding in Jinja2 ({% raw %}{{ comment.content }}{% endraw %}) converts <, >, &, ", and ' into their corresponding HTML entities, displaying the payload as harmless text without executing code.

Source Code Reference: app/templates/blog/post.html (line 55-60) & app/routes/blog.py:add_comment()
CWE-79

3. Reflected XSS — Silent Action Hijacking (Forced Comment)

Description & Root Cause: The search results banner reflects the q query parameter directly into the HTML response using Jinja2's | safe filter without output encoding. A crafted URL containing an HTML/JavaScript payload executes in the victim's browser the moment they open the link — without storing the script in the database.

Why HttpOnly Does Not Stop This: The application sets SESSION_COOKIE_HTTPONLY = True, so JavaScript cannot read document.cookie. However, same-origin fetch() requests executed by injected JavaScript automatically attach the victim's HttpOnly session cookie, allowing the attacker to silently forge authenticated actions (posting a comment under the victim's identity).

Target Feature: Post Search — :5000/?q=<payload> reflected in the "Showing results for:" banner, targeting POST /posts/2/comments.

Prerequisites: Toggle mode to Vulnerable Mode, and ensure the victim browser session is signed in on the blog (e.g., bob / bob123).

Demonstration Steps (Self-Propagating Chain)

  1. In Tab A (Attacker), sign in as alice (alice123) and paste the persuasive comment payload into /posts/1#comments (or skip to step 2 using the Direct Crafted URL).
  2. In Tab B / Incognito (Victim 1), sign in as bob (bob123), open /posts/1, and click alice's link "🔥 Top 10 Rust performance tips (must read)".
  3. Victim 1 briefly hits /?q=rust<script>..., which silently posts a natural-looking recommendation comment on Post #2 under @bob — carrying the exact same disguised trap link — then redirects bob to /?q=rust.
  4. Now sign in as another user (Victim 2, e.g., admin / admin123) and visit /posts/2#comments. Victim 2 sees trusted teammate @bob recommending the link, clicks it, and unwittingly spreads the forged comment under @admin as well!

Copyable Demonstration Payloads

In Vulnerable Mode the comment renders as normal prose with an enticing anchor link; the percent-encoded script in href stays hidden until clicked, and each victim's forged comment re-embeds the exact same trap link.
Decoded payload executed on reflection: rust<script>var u="/?q="+encodeURIComponent(new URLSearchParams(location.search).get("q"));fetch("/posts/2/comments",{method:"POST",body:new URLSearchParams({content:`Solid breakdown! Also check out these benchmarks: <a href="${u}">🔥 Top 10 Rust performance tips (must read)</a>`})}).then(function(){location.replace("/?q=rust")})</script>

Expected Behavior & Countermeasure Comparison

Aspect Stored XSS (Section 2) Reflected XSS (Section 3)
Payload Storage Persisted in SQLite comments table Not stored; delivered in URL parameter ?q=
Affected Victims Every user who visits /posts/1 Only users tricked into opening the crafted link
Demonstrated Impact Fake login modal steals password to C2 panel Silent fetch() forges comment despite HttpOnly

Vulnerable Mode: app/templates/blog/index.html renders {% raw %}{{ query | safe }}{% endraw %}, executing the injected script and silently submitting a comment as the logged-in victim before redirecting to /?q=rust.

Secure Mode: Jinja2 context-aware auto-escaping ({% raw %}{{ query }}{% endraw %}) encodes <script> into harmless HTML entities. The payload renders as plain text, no JavaScript runs, and no forged comment is created.
