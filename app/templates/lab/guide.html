Security Laboratory Demonstration Guide

Reference manual for instructors and presenters. Use this guide to walk through reproducible demonstrations of the SQL Injection Full Attack Chain (Reconnaissance to Account Takeover) and Stored Cross-Site Scripting.

CWE-89

1. SQL Injection (SQLi) — Full Attack Chain

Description & Root Cause: Untrusted user input is formatted directly into SQL query strings rather than bound using parameterized queries. This enables a realistic two-phase attack chain: first dumping users and hashes via search, then bypassing authentication to take over the administrator account.

Target Features: Post Search (/) and Account Login (/login)

Demonstration Steps

  1. Toggle mode to Vulnerable Mode via the floating switch in the bottom-right corner.

Phase 1: Reconnaissance & Data Exfiltration (Search)

An unauthenticated attacker explores the public search bar at the home page. They enter a UNION payload to dump all user records and password hashes:

The blog feed immediately displays all 8 user records from the users table, exposing usernames (including admin and alice) and their Argon2id password hashes.

Phase 2: Account Takeover via Authentication Bypass (Login)

Having identified that admin and alice exist, the attacker navigates to /login. Using their knowledge of Alice's account (password: alice123), they substitute Admin's password hash with Alice's hash:

Enter Alice's known password (alice123) into the Password field and click Sign In.

Expected Behavior

Vulnerable Mode: In Phase 1, the search query dumps the entire users table into the public feed. In Phase 2, the login query synthesizes an admin record carrying Alice's password hash, allowing the attacker to sign in as @admin with Alice's password.

Secure Mode: Both search and login use parameterized queries (? placeholder). The search bar treats the UNION string literally and returns 0 matching posts. The login page searches for a user whose literal username is the payload string, rejecting the attempt with 401 Unauthorized.

Source Code References: app/routes/blog.py:index() & app/routes/auth.py:login()
CWE-79

2. Stored Cross-Site Scripting (XSS)

Description & Root Cause: User-submitted comment text is stored in the database and later rendered in HTML templates without escaping, causing browser execution of attacker-supplied scripts.

Target Feature: Post Comments (/posts/1#comments)

Prerequisites: None (guests or logged-in users may comment).

Demonstration Steps

  1. Toggle mode to Vulnerable Mode.
  2. Navigate to Post 1 and scroll down to the Comments section.
  3. Submit a comment containing the copyable script payload:

Expected Behavior

Vulnerable Mode: The comment template renders with Jinja2's | safe filter, outputting raw HTML. When the page renders, the JavaScript modal executes immediately in the victim's browser.

Secure Mode: Context-aware output encoding translates HTML special characters (<, >, &) into HTML character entities. The script text is displayed harmlessly as plain text.

Source Code Reference: app/templates/blog/post.html & app/routes/blog.py:add_comment()
